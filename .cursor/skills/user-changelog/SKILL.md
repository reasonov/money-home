# User changelog

Собрать **только то, что интересно пользователю приложения**. Коротко, по делу, на русском. Без жаргона разработки.

## Диапазон

Определить `BASE..HEAD` по запросу пользователя:

| Запрос | BASE |
|--------|------|
| не указан / после push / unpushed | upstream `@{u}` (см. ниже) |
| последние N коммитов | `HEAD~N` |
| явный диапазон / SHA / тег | как сказал пользователь |

Upstream по умолчанию:

1. `git status -sb`, `git rev-parse --abbrev-ref @{u}`.
2. Если upstream нет — `origin/<branch>` или `origin/main`.
3. Если remote ещё нет — сказать, что push не было, и взять весь `HEAD` (или уточнить N у пользователя).

Незакоммиченное включать **только** когда диапазон — «после push» / по умолчанию. Для «последние N коммитов» и явного диапазона — только коммиты в диапазоне.

## Данные

1. Коммиты: `git log BASE..HEAD --pretty=format:'%h %s%n%b'`.
2. Diff: `git diff BASE..HEAD`. Для диапазона по умолчанию дополнительно: `git diff`, `git diff --cached`, `git status --porcelain`.
3. Читать diff и UI-копирайт затронутых экранов. Не читать SPEC целиком.

## Что включать

Только наблюдаемое пользователем:

- новые экраны, поля, кнопки, сценарии
- исправления багов, которые он мог заметить
- изменения формулировок в интерфейсе
- поведение офлайна/синхронизации, если оно видно в UI

Формулировать как для человека в приложении, не как для ревью кода.

## Что выкидывать

Рефакторинг, FSD, типы, миграции сами по себе, RLS, скиллы/правила Cursor, тесты, зависимости, внутренний sync/outbox, переименования без смены поведения.

Если пользовательского эффекта нет — так и написать, без списка «технических» пунктов.

## Формат ответа

Только текст в чат, без файла, без кода, без SHA и имён файлов.

```
Что нового

• одно изменение — одна строка
• ...
```

Если есть и фичи, и заметные фиксы — две секции: `Новое` и `Исправления`.

Пусто в диапазоне: `В выбранном диапазоне пользовательских изменений нет.` (для диапазона по умолчанию: `После последнего push пользовательских изменений нет.`)
