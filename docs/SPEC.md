# money-home — Product Spec

Семейное PWA для планирования покупок из общего бюджета и контроля баланса.

Источник требований для агентов. Код и UI не расширять за пределы текущего запроса и Acceptance Criteria ниже.

## Goal

Семья ведёт один счёт и один план покупок. Перед добавлением покупки на дату система считает, сколько денег будет на счёте к этой дате (текущий баланс + пополнения − уже запланированные траты), и либо сохраняет покупку, либо предлагает более позднюю дату. При завершении покупки («Готово») сумма вычитается из текущего баланса; запись остаётся в истории с итогом потраченного.

## Users & Access

- Целевые пользователи: члены одной семьи (супруги, дети).
- Auth: email + password (Supabase Auth).
- После входа пользователь создаёт `Household` или присоединяется по invite-коду.
- Все члены одного household видят и редактируют общий баланс, правила пополнений и план покупок (роли v1 не различаем).

## Stack

| Layer | Choice |

| Architecture | Feature-Sliced Design (`app`, `pages`, `widgets`, `features`, `entities`, `shared`) |

| Currency | RUB |

UI-kit в v1 не обязателен. Секреты (`service_role`) только на сервере/в CI; в клиенте — `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`.

## Current stage (mock → Supabase)

Целевой бэкенд — Supabase (Auth, Postgres, RLS, Realtime). Сейчас UI и домен работают на **временном client-side mock** (`localStorage`), пока бэкенд не подключён.

На этапе mock допустимо:

- Auth без реальной проверки пароля / уникальности email
- Create/join household локально; join создаёт локальную семью с введённым кодом (не серверный join)
- Seed демо-данных (баланс, правила, покупки, Activity) после create/join
- Activity из seed; генерация из Realtime чужих изменений — после подключения Supabase

Не считать mock целевой архитектурой. При переходе на Supabase:

- Заменить stores/persistence на Auth + Postgres + RLS
- Реализовать настоящий invite join (RPC / контролируемый insert по коду)
- Realtime → обновление stores и лента Activity только от других членов
- Убрать или отключить demo-seed как источник «живой» семьи

## Design / Identity (v1)

Концепция: **«Домашний календарь»** — семейный планировщик покупок из общего бюджета, не банк и не трекер категорий.

Метафора: общая доска дома — что купим и когда хватит денег. Тон спокойный, тёплый, читаемый; mobile-first (PWA).

| Token | Value |
| --- | --- |
| Background | светло-серо-голубой `#F2F5F7` (тёмная тема — свои CSS-переменные через `data-theme`) |
| Surface | белый `#FFFFFF` |
| Text | почти чёрный `#0F172A` |
| Accent | мягкий teal `#0F766E` |
| Success / «хватит» | sage `#15803D` |
| Warning / «не хватит» | terracotta `#C2410C` |
| Typography | геометрический sans (Manrope или Plus Jakarta Sans); суммы — tabular nums |
| Radius | 12–16px (без pills) |
| Brand | wordmark Money Home в шапке; отдельный логотип-иконка в v1 не обязателен |
| Theme | светлая / тёмная / система; выбор в «Ещё», хранение preference локально |

UI-принципы:

- Баланс — главный визуальный якорь экрана; рядом — «свободно до пополнения» (`balance − planned` с датой строго раньше следующего начисления). Тап по сумме баланса открывает быстрое редактирование.
- Главная: баланс, CTA новой покупки, план покупок и компактный вход в историю (итог «всего потрачено» + переход); полный список истории — на отдельном экране. Карточки только для интерактива.
- Нижняя навигация (иконка + подпись): Главная · История · Доход · Ещё. Создание покупки — CTA на главной (и экран `/purchases/new`), не отдельный таб.
- В плане даты относительные («Сегодня», «Завтра», «Просрочено» / дата); статус «В плане» на карточке не дублировать.
- У покупки опциональное многострочное описание (`notes`) — свободный текст или список позиций; в карточке плана и истории описание по умолчанию свёрнуто.
- Вердикт проекции (`canAfford` / отказ) читается сразу: цвет + короткий русский текст в баннере; развёрнутый отказ — в нижнем дровере. При отказе — действия: поставить на `nextAffordableDate`, при необходимости уменьшить сумму до projected; если пополнений нет — ссылка на экран пополнений.
- Подтверждение: «Готово» по клику на кнопку / из меню «⋯», отмена покупки, удаление правила, выход. Свайп «Готово» на карточке плана — **без** confirm.
- Feedback: toast при копировании кода и коротких успехах; empty states с CTA; loading/skeleton на отложенной загрузке; мягкое обновление сумм при Realtime.
- Доступность: видимый `:focus-visible`, focus trap в дроверах, `role="alert"` на ошибках форм, hit target ≥ 44px у основных действий.
- Пользовательский copy — только русский (без «household» / «Invite» в UI): «семья», «код приглашения».
- Без фиолетовых градиентов, glow, стат-стрипов и детского/игрового стиля; тёмная тема — спокойная, не «финтех-glow».
- Сложный UI-kit не строить: достаточно CSS-переменных и аккуратных экранов.

Референсы настроения (не копировать UI): Hearth Display, Cozi, AnyList.

## Domain Model

### Household

- `id`, `name`, `invite_code` (уникальный код для join), timestamps.

### Member

- Связь `user_id` ↔ `household_id`.
- Один пользователь — один household в v1.

### Balance

- Текущий баланс household (число, RUB).
- Редактируется вручную любым членом семьи; также уменьшается автоматически при «Готово» на сумму покупки.
- На главной рядом показывается «свободно до пополнения» (см. Features → Balance).

### IncomeRule

Регулярное пополнение:

- `amount` (RUB, > 0)
- `frequency`: `weekly` | `biweekly` | `monthly`
- для `weekly` / `biweekly`: день недели (`weekday`, 0=вс … 6=сб; в коде — `Date.getDay()`)
- для `monthly`: день месяца (`month_day`, 1–28 в v1, чтобы избежать неоднозначности 29–31)
- `anchor_date` (для `biweekly` — точка отсчёта двухнедельного цикла)
- `active` (bool)

У household может быть несколько правил.

### Purchase

Трата (план или история):

- `title` (короткое название)
- `amount` (> 0, RUB)
- `planned_date` (date) — плановая / фактическая дата покупки
- `notes` (optional, string) — свободное многострочное описание или список позиций; не влияет на проекцию
- `status`: `planned` | `done` | `cancelled`
  - в проекции баланса и «свободно до пополнения» участвуют только `planned`
  - `done` — история; сумма всех `done` = «всего потрачено»; при переходе `planned` → `done` текущий баланс уменьшается на `amount`
  - `cancelled` — скрыты из плана и истории; баланс не меняется
- `created_by` (user id)

### Activity (in-app)

Событие изменения данных household другим членом семьи (не push):

- `kind`: `purchase_created` | `purchase_updated` | `purchase_done` | `purchase_cancelled` | `balance_updated` | `income_rule_changed`
- `actor_id`, `actor_name` (отображаемое имя автора изменения)
- `purchase_id` (optional) — связь с покупкой, если событие про неё
- `summary` — короткий русский текст для ленты
- `created_at`
- `seen_at` (nullable) — момент просмотра получателем (клик по покупке / повторный заход на главную / открытие ленты)

Собственные действия текущего пользователя в ленту не попадают.

## Balance Projection Algorithm

Чистая функция (без I/O). Реализация — в `shared` domain helper; UI только вызывает её.

### Inputs

- `currentBalance: number`
- `asOfDate: Date` (сегодня / дата «сейчас» для расчёта; обычно local date пользователя)
- `targetDate: Date` (дата покупки, `targetDate >= asOfDate`)
- `incomeRules: IncomeRule[]` (только active)
- `plannedPurchases: Purchase[]` (status=`planned`, даты в `(asOfDate, targetDate]` — включительно target, исключительно asOf если покупка «сегодня» уже учтена в балансе; см. правило ниже)
- `candidateAmount: number` (сумма новой покупки)

### Rules

1. Стартовый баланс = `currentBalance`.
2. Пополнения: для каждого active `IncomeRule` найти все даты начисления `d`, где `asOfDate < d <= targetDate`, суммировать `amount`.
3. Запланированные траты: суммировать `amount` всех `planned` с `asOfDate < planned_date <= targetDate` (покупки на `asOfDate` считаются уже отражёнными в ручном балансе и **не** вычитаются снова).
4. `projectedBalance = currentBalance + incomes - plannedSpend`.
5. `canAfford = projectedBalance >= candidateAmount`.

### Outputs

- `projectedBalance`
- `canAfford`
- всегда (для UI breakdown):
  - `shortfall` = `max(0, candidateAmount - projectedBalance)`
  - `plannedBeforeTarget[]`: `{ title, amount, plannedDate }` — `planned` в `(asOfDate, targetDate]` (исключая редактируемую запись, если задан `excludePurchaseId`)
  - `incomeTotal`, `incomeOccurrencesCount` — сумма и число начислений к `targetDate` (итог по всем active rules; поминутная разбивка по правилам в v1 не обязательна)
  - `nextAffordableDate: Date | null` — ближайший день `d >= targetDate`, на котором `canAfford` для той же `candidateAmount`; поиск по дням, горизонт **365 дней** от `asOfDate`; если не найдено — `null`
- при отказе:
  - короткий `message` (баннер), например:  
    `К 25.08.2026 будет 1 500 ₽ — не хватает 800 ₽`
  - развёрнутый отказ в нижнем дровере:
    - заголовок: `Не хватает денег к выбранной дате`
    - к дате будет X ₽, не хватает Y ₽ на покупку Z ₽
    - блок «Уже в плане до этой даты» (список `title — amount`) или «Других покупок до этой даты нет»
    - блок «Ожидаемые пополнения: N ₽ (M начислений)» или «Пополнений до этой даты не ожидается» + CTA на `/income`, если начислений 0
    - «Ближайшая дата, когда хватит: ДД.ММ.ГГГГ» с кнопкой «Поставить на эту дату» (подставляет `nextAffordableDate` в поле даты и закрывает дровер) или «В ближайший год подходящей даты нет…»
    - если `projectedBalance > 0` и `!canAfford` — опциональная кнопка уменьшить сумму до projected balance

Расчёт — чистая клиентская функция в `shared` (данные из store/API). Серверный пересчёт (Edge/RPC) в v1 не требуется.

### Available until next income

Отдельный helper для главной:

- `nextIncomeDate` — ближайшая дата начисления по active rules после `asOfDate` (горизонт 365 дней)
- `plannedSpend` — сумма `planned` с `planned_date < nextIncomeDate` (включая сегодня и просроченные `planned`; покупки в день пополнения не входят)
- если правил пополнения нет — сумма всех `planned` с датой в горизонте 365 дней
- `available = currentBalance − plannedSpend`
- если `available < 0` — подсказка, что сделать (перенести покупки / изменить даты или сумму)

### Example (acceptance)

- Баланс сейчас: такой, что к 25 августа с учётом пополнений и планов будет 1500 ₽.
- Покупка: «штора», 2300 ₽, дата 25 августа.
- Ожидание: отказ; баннер с projectedBalance и shortfall; дровер с breakdown и CTA на ближайшую дату; покупка не создаётся.
- Если к дате ≥ 2300 ₽ — покупка сохраняется в календарь/`planned`.

## Features (v1)

### Auth

- [ ] Регистрация / вход email+password
- [ ] Выход (с подтверждением)
- [ ] Защита роутов: без сессии → login; без household → onboarding create/join

### Household

- [ ] Создать household → шаг «Пригласите семью»: крупный код приглашения; «Поделиться» (`navigator.share`, fallback — копирование), «Скопировать», затем «Продолжить»
- [ ] Войти в household по коду приглашения (на mock — локальная семья с этим кодом + seed; целевое — настоящий join через Supabase)
- [ ] Показать текущий код в настройках (копирование → toast «Скопировано»)

### Balance

- [ ] Показать текущий баланс
- [ ] Рядом с балансом показать «свободно до пополнения»; при отрицательном — guidance-hint
- [ ] Редактировать баланс вручную (настройки и тап по сумме на главной)
- [ ] При «Готово» уменьшить баланс на сумму покупки; confirm списания — при клике на кнопку / пункт меню, не при свайпе
- [ ] Realtime/refresh при изменении другим членом; UI мягко обновляет суммы (transition / без резких скачков)

### Income rules

- [ ] Создать правило (сумма + частота + параметры дня); новые — `active: true`
- [ ] Редактировать поля существующего правила (сумма, частота, день / weekday / `anchor_date`)
- [ ] Включить / выключить правило (`active`) без удаления
- [ ] Удаление — с подтверждением
- [ ] Учитывать только `active` правила в проекции и в «свободно до пополнения»
- [ ] Empty state объясняет зачем правила + якорь к форме добавления

### Purchases

- [ ] Список запланированных покупок (`planned`) по датам; просроченные визуально выделены и выше актуальных
- [ ] Карточка: primary «Готово», меню «⋯» для «Изменить» / «Отмена»; hit target ≥ 44px
- [ ] Свайп влево на карточке плана → «Готово» + списание **без** confirm
- [ ] При создании: поля title, amount, planned_date, optional `notes`
- [ ] Перед созданием: проекция; при `canAfford` — сохранить; иначе — баннер + дровер с breakdown, CTA даты/суммы, ссылка на пополнения при отсутствии incomes
- [ ] В карточке плана и истории: `notes` по умолчанию скрыты; «Показать описание» / «Скрыть описание»
- [ ] Редактирование `planned` через проекцию (exclude себя); при `!canAfford` — баннер + дровер с теми же CTA
- [ ] Отмена → `cancelled` (с подтверждением)
- [ ] Done по клику (кнопка / меню) → confirm → `done` + списание `amount`
- [ ] Empty state плана: CTA «Добавить покупку» и «Настроить пополнение»

### Purchase history

- [ ] Отдельный экран «История покупок» (`/history`): все `done`, группировка по дате (новые сверху)
- [ ] В нижней навигации — таб «История»; на главной — компактный тизер; в «Ещё» — ссылка на историю
- [ ] Empty state истории с CTA на план / новую покупку
- [ ] В истории: title, amount, date; optional notes — свёрнуты/раскрываются как в плане

### Activity feed (in-app)

Источник событий — Realtime-изменения balance / purchases / income_rules (и mock-seed до подключения бэка). Не путать с push.

- [ ] Лента последних изменений household в дровере из шапки (иконка «колокольчик»)
- [ ] В ленте: summary, имя автора, относительное время; непросмотренные визуально отличаются
- [ ] Счётчик непросмотренных на иконке в шапке
- [ ] У `planned`-покупки с непросмотренным событием (`purchase_id`) — точка-бейдж у названия; снимается при клике на карточку покупки, при повторном открытии главной (после того как точка уже была показана) или при открытии ленты уведомлений
- [ ] Открытие ленты помечает все события просмотренными
- [ ] События только от других членов; свои действия не создавать
- [ ] Клик по событию с `purchase_id`: если покупка `planned` — переход на edit; если `done` — на историю; иначе закрыть ленту

### Settings («Ещё»)

- [ ] Блок «Семья»: название, код приглашения, копирование
- [ ] Блок «Баланс»: форма ручного редактирования
- [ ] Блок «Оформление»: переключатель темы — светлая / тёмная / система
- [ ] Блок «Разделы»: ссылки на историю, пополнения, новую покупку
- [ ] Блок «Аккаунт»: текущий email, выход с подтверждением

### PWA & shell

- [ ] `vite-plugin-pwa`: installable app, базовый precache; не offline-first conflict sync
- [ ] Контент main не перекрывается sticky bottom nav (padding + safe-area)
- [ ] Sticky header с wordmark; на экранах с household — иконка ленты Activity

### Accessibility & feedback

- [ ] `:focus-visible` на интерактивах; focus trap + возврат фокуса в дроверах
- [ ] Ошибки форм: `role="alert"`
- [ ] Toast для коротких подтверждений (копирование кода и т.п.)
- [ ] Skeleton при ожидании данных формы редактирования покупки

## Non-Goals (v1)

- Мультивалютность, кредиты, категории бюджета, банковские интеграции
- Несколько household на пользователя
- Роли/права внутри семьи (admin vs child)
- Offline-first sync конфликтов (PWA install + базовый cache ок; конфликтная синхронизация — позже)
- Push-уведомления, email-дайджесты (in-app лента Activity — в scope v1)
- Откат списания баланса при отмене уже завершённой (`done`) покупки
- Редактирование покупок со статусом `done` / `cancelled`
- Структурированные line-items вместо свободного `notes`
- Сложный UI-kit / дизайн-система с нуля (достаточно аккуратного UI)
- Отдельный wide desktop-layout (достаточно mobile column)

## Supabase Expectations

Целевой persistence вместо mock. При подключении закрыть gaps из раздела «Current stage».

- Таблицы под сущности выше; у `purchases` — колонка `notes` (text, nullable).
- RLS: доступ только членам того же `household_id`.
- Invite join — через RPC или контролируемый insert с проверкой кода (не открывать таблицы без RLS); join присоединяет к существующему household, не создаёт новый с тем же кодом.
- Realtime на balance / purchases / income_rules по household; клиент строит Activity из чужих изменений и обновляет stores.
