# money-home — Product Spec

PWA для учёта расходов и доходов по счетам, с планированием покупок.

Источник требований для агентов. Код и UI не расширять за пределы текущего запроса и Acceptance Criteria ниже.

## Goal

Пользователь ведёт личные счета: расходы и доходы по категориям, переводы между счетами, авто-пополнения. Отдельный счёт можно расшарить кодом — тогда баланс, операции, правила и план покупок по этому счёту общие. Перед запланированной покупкой система считает, хватит ли денег на выбранном счёте к дате (баланс + ещё не начисленные пополнения − другие планы); если не хватает — предлагает более позднюю дату или перевод с другого счёта. «Готово» по покупке списывает сумму и создаёт расход.

## Users & Access

- Auth: email + password (Supabase Auth).
- После входа — сразу приложение (свои счета). Household как «одна семья на всё» нет.
- Один пользователь — много счетов. Счёт можно создать или присоединиться по коду.
- Члены одного счёта видят и редактируют его данные наравне (роли v1 не различаем). Owner — создатель; leave может не-owner.

- Без фиолетовых градиентов, glow и детского стиля.
- Сложный UI-kit не строить: CSS-переменные и аккуратные экраны.

## Domain Model

### Profile

- `user_id`, `display_name`.

### Account

- `id`, `name`, `amount` (текущий баланс, RUB), `owner_id`, `invite_code` (nullable unique; появляется при шаринге), timestamps.
- Создатель сразу член и owner.

### AccountMember

- `(account_id, user_id)`.

### Category

- `kind`: `expense` | `income`
- `name`, `color` (из палитры), `icon` (ключ из набора SVG), `created_by`
- Привязка ко счетам через `category_accounts` (M2M).
- При создании категории по умолчанию отмечены все текущие счета пользователя.
- При создании/редактировании счёта — чеклист категорий, которые пользователь уже видит.
- На общем счёте привязанные категории общие: любой член читает и редактирует. Unlink с одного счёта не удаляет категорию с других. Unlink с последнего счёта удаляет категорию.
- Правка имени/цвета/иконки одна на сущность — меняется везде, где категория привязана.

### Transaction

Posted-операция:

- `kind`: `expense` | `income` | `transfer`
- `account_id`; для перевода ещё `counterparty_account_id` (куда)
- `category_id` (nullable), снимки `category_name`, `category_color`, `category_icon`
- `amount` (> 0), `occurred_on`, `title?`, `notes?`
- `status`: `posted` | `cancelled`
- `source`: `manual` | `income_rule` | `purchase`
- `created_by`

Расход уменьшает баланс, доход увеличивает, перевод — атомарно оба счёта. В истории — `posted`.

### Purchase

План покупки (не posted-расход, пока не «Готово»):

- `title`, `amount`, `planned_date`, `notes?`
- `account_id`, `category_id`, снимки категории
- `status`: `planned` | `done` | `cancelled`
- в проекции только `planned`
- дата сама не списывает: просроченные визуально выделены; пользователь жмёт «Готово» или «Отмена»
- «Готово» → расход (`source=purchase`) + списание со счёта

### IncomeRule

Регулярное авто-пополнение счёта (фактическая проводка в календарный день):

- `account_id`, `amount` (> 0), `title?`, `category_id?`
- `frequency`: `weekly` | `biweekly` | `monthly`
- `weekly` / `biweekly`: `weekday` (0=вс … 6=сб)
- `monthly`: `month_day` 1–28
- `anchor_date` для `biweekly`
- `active`

### IncomeOccurrence

- уникально `(income_rule_id, occurred_on)`
- `status`: `posted` | `skipped` | `adjusted`
- `transaction_id?`
- не переначислять skipped; миграция старых правил задним числом не доначисляет

### Activity (in-app)

- `kind`: `purchase_created` | `purchase_updated` | `purchase_done` | `purchase_cancelled` | `account_updated` | `income_rule_changed` | `transaction_created` | `income_auto_posted`
- свои действия в ленту не попадают, **кроме** `income_auto_posted` (всем членам счёта, включая того, кто открыл приложение)
- `transaction_id` / `purchase_id` optional

## Auto income

Правило задаёт календарный день, не час. Проводка за день D — когда наступает D.

- RPC `apply_due_income_rules(p_as_of date)`: даты `created_at::date <= d <= p_as_of` по active rules, без существующего occurrence. Unique + `on conflict do nothing`.
- Клиент вызывает при bootstrap (локальная дата). Catch-up пропущенных дней.
- Уведомление в ленте. **Отменить** — сторно, status `skipped`. **Изменить** — новая сумма > 0, status `adjusted`.

## Balance Projection Algorithm

Чистая функция (без I/O) **по одному счёту**.

### Inputs

- `currentBalance` этого счёта
- `asOfDate`, `targetDate` (`targetDate >= asOfDate`)
- `incomeRules` — active правила **этого** счёта
- `postedOccurrenceDates` — даты, по которым occurrence уже есть (posted/skipped/adjusted) — в прогноз не входят
- `plannedPurchases` — `planned` **этого** счёта
- `candidateAmount`
- `excludePurchaseId?`

### Rules

1. Стартовый баланс = `currentBalance` (уже включает прошедшие авто-пополнения).
2. Пополнения: даты `d` где `asOfDate < d <= targetDate`, нет occurrence, суммировать `amount`.
3. Планы: `planned` с `asOfDate < planned_date <= targetDate` (покупки на `asOfDate` не вычитаются).
4. `projectedBalance = currentBalance + incomes - plannedSpend`.
5. `canAfford = projectedBalance >= candidateAmount`.

### Outputs

Как раньше: `projectedBalance`, `canAfford`, `shortfall`, `plannedBeforeTarget`, `incomeTotal`, `incomeOccurrencesCount`, `nextAffordableDate` (горизонт 365 дней), `message`.

При отказе дополнительно: счета пользователя, у которых `available` (баланс − planned до target, без чужих счетов) ≥ `shortfall` — предложение перевести `shortfall` ₽. После перевода — повторная проекция и сохранение покупки.

### Available until next income

По карточке счёта: ближайшая **будущая** дата правила без occurrence; `planned` с датой строго раньше этой даты (включая сегодня и просроченные).

### Example (acceptance)

- На счёте к 25 августа с учётом будущих пополнений и планов будет 1500 ₽.
- Покупка: «штора», 2300 ₽, 25 августа, категория расхода, этот счёт.
- Ожидание: отказ; если на другом счёте пользователя свободно ≥ 800 ₽ — CTA «Перевести 800 ₽ со счёта …».

## Features (v1)

### Auth

- [ ] Регистрация / вход email+password
- [ ] Выход с подтверждением
- [ ] Без сессии → login; с сессией → главная (onboarding семьи нет)
- [ ] После первого входа без счетов — интерактивные подсказки: заполнить счёт, категории, расход и доход (шаг можно пропустить); показать тему, авто-пополнения, планирование и шаринг; повтор из «Настройки»

### Accounts

- [ ] Создать счёт (имя, стартовый баланс, чеклист категорий)
- [ ] Поделиться: код счёта, копирование / share
- [ ] Присоединиться по коду («Добавить счёт») — тот же счёт, не копия
- [ ] Покинуть счёт (не owner)
- [ ] Список счетов на отдельной странице; в меню — до трёх счетов и ссылка «Все счета»; личные и общие отличаются
- [ ] Редактировать имя и баланс; привязать категории
- [ ] Перевод между своими счетами (пользователь — член обоих)

### Categories

- [ ] CRUD: имя, цвет, иконка, kind, счета (дефолт все)
- [ ] На форме счёта — чеклист доступных категорий
- [ ] На общем счёте все члены видят и правят
- [ ] В расход/доход/покупку/правило — только категории выбранного счёта и нужного kind

### Expenses & income

- [ ] Добавить расход: счёт, категория расхода, сумма, дата, optional title/notes → сразу списание
- [ ] Добавить доход: счёт, категория дохода, сумма, дата → сразу зачисление
- [ ] Если на главной выбран конкретный счёт — он подставляется в форму расхода/дохода
- [ ] Главная: posted операции за выбранный период, фильтр по типу; счёт — в шапке

### Income rules

- [ ] CRUD правила на конкретном счёте; optional категория дохода
- [ ] Только active начисляются и участвуют в проекции будущих дат
- [ ] Catch-up при входе; уведомление; отмена / правка начисления

### Purchases (planning)

- [ ] Список `planned` по датам; просроченные сверху; фильтр по счёту в шапке
- [ ] Создание: title, amount, date, счёт, категория расхода, notes; проекция; отказ + перевод
- [ ] Редактирование planned через проекцию (exclude себя)
- [ ] «Готово» → расход + списание; отмена → `cancelled`
- [ ] Свайп «Готово» без confirm; кнопка/меню — с confirm

### Home chart

- [ ] Кольцевой график по категориям: расходы или доходы (табы)
- [ ] Период: день / неделя / месяц / год / произвольный диапазон
- [ ] Фильтр по счёту в шапке, включая «все счета»

### Statistics

- [ ] Страница в нижней навигации: расходы и доходы за период
- [ ] Фильтр по счёту в шапке и периоду (день / неделя / месяц / год / произвольный диапазон)
- [ ] Один график на странице, выбор вида
- [ ] Расходы и доходы по категориям (кольцевой график)
- [ ] Расходы по дням недели (столбцы)
- [ ] Тепловая карта расходов по дням
- [ ] Динамика расходов и доходов
- [ ] Топ операций
- [ ] По счетам, если в шапке «все счета»
- [ ] Сравнение сводки с прошлым периодом
- [ ] Средний расход в день и доля расходов от доходов

### Settings

- [ ] Сайдбар: до трёх счетов и «Все счета», категории, авто-пополнения, перевод, настройки
- [ ] Настройки: тема; имя; email; подсказки; выход

### PWA & shell

- [ ] Installable PWA; sticky nav + safe-area; шапка (меню, счёт или заголовок, уведомления) + лента Activity

### Accessibility & feedback

## Non-Goals (v1)

- Мультивалютность, кредиты, бюджеты, банковские интеграции
- Разрезы статистики: траты в день зарплаты
- Типы счетов (карта/нал)
- Произвольные картинки иконок (только набор SVG)
- Начисление в конкретный час
- Несколько независимых «семей» как сущность; шаринг только счёт
- Роли внутри счёта
- Offline-first conflict sync
- Push, email
- Откат done-покупки; редактирование done/cancelled покупок
- Удаление owner-счёта с участниками (leave + invalidate code)
- Сложный UI-kit / wide desktop-layout

## Supabase Expectations

- Таблицы: `profiles`, `accounts`, `account_members`, `categories`, `category_accounts`, `transactions`, `income_occurrences`; `income_rules` и `purchases` с `account_id`.
- RLS: данные счёта iff член; категория видна/редактируема, если член хотя бы одного привязанного счёта.
- Join счёта — RPC по коду.
- Realtime по счетам пользователя.
- RPC авто-пополнения идемпотентны.
