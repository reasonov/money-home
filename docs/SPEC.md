# money-home — Product Spec

PWA для учёта расходов и доходов по счетам, с планированием покупок.

Источник требований для агентов. Код и UI не расширять за пределы текущего запроса и Acceptance Criteria ниже.

## Goal

Пользователь ведёт личные счета: расходы и доходы по категориям, переводы между счетами, авто-пополнения и регулярные расходы. Отдельный счёт можно расшарить кодом — тогда баланс, операции, правила и план покупок по этому счёту общие. Перед запланированной покупкой система считает, хватит ли денег на выбранном счёте к дате (баланс + ещё не начисленные пополнения − планы − ещё не списанные регулярные расходы); если не хватает — предлагает более позднюю дату или перевод с другого счёта. «Готово» по покупке списывает сумму и создаёт расход.

## Users & Access

- Auth: email + password (Supabase Auth). Сброс пароля письмом и смена пароля в профиле.
- После входа — сразу приложение (свои счета). Household как «одна семья на всё» нет.
- Один пользователь — много счетов. Счёт можно создать или присоединиться по коду.
- Члены одного счёта видят и редактируют его данные наравне (роли v1 не различаем). Owner — создатель; leave может не-owner.

- Главная: сумма по выбранному счёту (или всем без счетов с `exclude_from_total`), CTA «Расход» / «Доход» с плюсом сразу под суммой, лента событий на 7 дней (планы, пополнения, регулярные расходы), кольцевой график по категориям (по клику — доля категории), период день/неделя/месяц/год/произвольный, табы «Расходы» / «Доходы».
- Нижняя навигация: Главная · Статистика · Планирование · Перевод; по центру «+», наполовину над панелью (тап — дровер расхода; удержание — доход).
- Боковое меню: wordmark Money Home, до трёх счетов и ссылка «Все счета», категории, регулярные операции, перевод, настройки.
- Вердикт проекции (`canAfford` / отказ) читается сразу: цвет + короткий русский текст; развёрнутый отказ — в нижнем дровере. При отказе — дата, сумма, пополнения, перевод с другого счёта.
- Пользовательский copy — только русский: «счёт», «поделиться счётом», «код счёта». Без «household» / «Invite» в UI.
- Без фиолетовых градиентов, glow и детского стиля.
- Сложный UI-kit не строить: CSS-переменные и аккуратные экраны.

## Domain Model

### Profile

- `user_id`, `display_name`, `preferences` (json персонализации; по умолчанию предложения при вводе суммы включены).

### Account

- `id`, `name`, `amount` (текущий баланс, RUB), `owner_id`, `invite_code` (nullable unique; появляется при шаринге), `exclude_from_total` (не входит в сумму «все счета» на главной), timestamps.
- Создатель сразу член и owner.

### AccountMember

- `(account_id, user_id)`.

### Category

- `kind`: `expense` | `income`
- `name`, `color` (из палитры), `icon` (ключ из набора SVG), `created_by`
- Привязка ко счетам через `category_accounts` (M2M).
- При создании категории по умолчанию отмечены все текущие счета пользователя.
- При создании/редактировании счёта — чеклист категорий, которые пользователь уже видит.
- На общем счёте привязанные категории общие: любой член читает и редактирует. Unlink с одного счёта не удаляет категорию с других. Unlink с последнего счёта удаляет категорию.
- Правка имени/цвета/иконки одна на сущность — меняется везде, где категория привязана.

### Transaction

Posted-операция:

- `kind`: `expense` | `income` | `transfer`
- `account_id`; для перевода ещё `counterparty_account_id` (куда)
- `category_id` (nullable), снимки `category_name`, `category_color`, `category_icon`
- `amount` (> 0), `occurred_on`, `title?`, `notes?`
- `status`: `posted` | `cancelled`
- `source`: `manual` | `income_rule` | `expense_rule` | `purchase`
- `created_by`

Расход уменьшает баланс, доход увеличивает, перевод — атомарно оба счёта. В истории — `posted`.

### Purchase

План покупки (не posted-расход, пока не «Готово»):

- `title`, `amount`, `planned_date`, `notes?`
- `account_id`, `category_id`, снимки категории
- `status`: `planned` | `done` | `cancelled`
- в проекции только `planned`
- дата сама не списывает: просроченные визуально выделены; пользователь жмёт «Готово» или «Отмена»
- «Готово» → расход (`source=purchase`) + списание со счёта

### IncomeRule

Регулярное авто-пополнение счёта (фактическая проводка в календарный день):

- `account_id`, `amount` (> 0), `title?`, `category_id?`
- `frequency`: `weekly` | `biweekly` | `monthly`
- `weekly` / `biweekly`: `weekday` (0=вс … 6=сб)
- `monthly`: `month_day` 1–28
- `anchor_date` для `biweekly`
- `active`

### IncomeOccurrence

- уникально `(income_rule_id, occurred_on)`
- `status`: `posted` | `skipped` | `adjusted`
- `transaction_id?`
- не переначислять skipped; миграция старых правил задним числом не доначисляет

### ExpenseRule

Регулярный авто-расход счёта (аренда, подписка; фактическая проводка в календарный день):

- те же поля расписания, что у IncomeRule
- `category_id?` — категория расхода
- `active`

### ExpenseOccurrence

- уникально `(expense_rule_id, occurred_on)`
- `status`: `posted` | `skipped` | `adjusted`
- `transaction_id?`
- не пересписывать skipped; старые правила задним числом не досписывают

### Activity (in-app)

- `kind`: `purchase_created` | `purchase_updated` | `purchase_done` | `purchase_cancelled` | `account_updated` | `income_rule_changed` | `expense_rule_changed` | `transaction_created` | `income_auto_posted` | `expense_auto_posted`
- свои действия в ленту не попадают, **кроме** `income_auto_posted` и `expense_auto_posted` (всем членам счёта, включая того, кто открыл приложение)
- `transaction_id` / `purchase_id` optional

## Auto income & expense

Правило задаёт календарный день, не час. Проводка за день D — когда наступает D.

- RPC `apply_due_income_rules(p_as_of date)` / `apply_due_expense_rules(p_as_of date)`: даты `starts_on <= d <= p_as_of` по active rules, без существующего occurrence. Unique + `on conflict do nothing`.
- Доход зачисляет, расход списывает. Клиент вызывает оба при bootstrap (локальная дата). Catch-up пропущенных дней.
- Уведомление в ленте. **Отменить** — сторно, status `skipped`. **Изменить** — новая сумма > 0, status `adjusted`.

## Balance Projection Algorithm

Чистая функция (без I/O) **по одному счёту**.

### Inputs

- `currentBalance` этого счёта
- `asOfDate`, `targetDate` (`targetDate >= asOfDate`)
- `incomeRules` — active правила пополнения **этого** счёта
- `expenseRules` — active правила расхода **этого** счёта
- `postedOccurrenceDates` / `postedExpenseOccurrenceDates` — даты, по которым occurrence уже есть (posted/skipped/adjusted) — в прогноз не входят
- `plannedPurchases` — `planned` **этого** счёта
- `candidateAmount`
- `excludePurchaseId?`

### Rules

1. Стартовый баланс = `currentBalance` (уже включает прошедшие авто-пополнения и авто-расходы).
2. Пополнения: даты `d` где `asOfDate < d <= targetDate`, нет occurrence, суммировать `amount`.
3. Регулярные расходы: тот же интервал, нет occurrence, суммировать `amount`.
4. Планы: `planned` с `asOfDate < planned_date <= targetDate` (покупки на `asOfDate` не вычитаются).
5. `projectedBalance = currentBalance + incomes - plannedSpend - expenseRuleSpend`.
6. `canAfford = projectedBalance >= candidateAmount`.

### Outputs

Как раньше: `projectedBalance`, `canAfford`, `shortfall`, `plannedBeforeTarget`, `incomeTotal`, `incomeOccurrencesCount`, `nextAffordableDate` (горизонт 365 дней), `message`.

При отказе дополнительно: счета пользователя, у которых `available` (баланс − planned до target, без чужих счетов) ≥ `shortfall` — предложение перевести `shortfall` ₽. После перевода — повторная проекция и сохранение покупки.

### Available until next income

По карточке счёта: ближайшая **будущая** дата пополнения без occurrence; из баланса вычитать `planned` с датой строго раньше этой даты (включая сегодня и просроченные) и будущие регулярные расходы строго до этой даты.

### Example (acceptance)

- На счёте к 25 августа с учётом будущих пополнений и планов будет 1500 ₽.
- Покупка: «штора», 2300 ₽, 25 августа, категория расхода, этот счёт.
- Ожидание: отказ; если на другом счёте пользователя свободно ≥ 800 ₽ — CTA «Перевести 800 ₽ со счёта …».

- [ ] Главная: posted операции за выбранный период, фильтр по типу; счёт — в шапке

- Мультивалютность, кредиты, бюджеты, банковские интеграции
- Разрезы статистики: траты в день зарплаты

- Начисление в конкретный час

- Роли внутри счёта
- Push; продуктовые email (Auth-письма восстановления пароля — да)

- Сложный UI-kit / wide desktop-layout

## Supabase Expectations

- Таблицы: `profiles` (`preferences` jsonb), `accounts`, `account_members`, `categories`, `category_accounts`, `transactions`, `income_occurrences`, `expense_occurrences`; `income_rules`, `expense_rules` и `purchases` с `account_id`.
- RLS: данные счёта iff член; категория видна/редактируема, если член хотя бы одного привязанного счёта.
- Join счёта — RPC по коду.
- Realtime по счетам пользователя.
- RPC авто-пополнений и авто-расходов идемпотентны.
